## 重要指摘事項（優先度順）

### [High] search() 関数の引数が 16〜17 個 — SearchParams 構造体への抽出
- 指摘者: System Architect, Maintainability Guardian, Legacy Bridge Architect, Refactoring Evangelist, Tuning Expert
- 場所: `core/src/search.rs:129-147`
- 影響: 引数順序のミスリスク、保守性の低下、新しいパラメータ追加時の呼び出し元修正が必須
- 対処: `SearchRequest` 構造体を作り、パラメータをまとめること。handlers.rs でも `Default` impl でサーバー向けの適切なデフォルト値を設定

### [High] VLM ランタイムが同期コンテキスト内でネスト作成され、panic の可能性
- 指摘者: System Architect
- 場所: `core/src/vlm.rs:29-37`、呼び出し元 `core/src/indexer.rs:457`
- 影響: MCP サーバーや HTTP ハンドラから呼ばれた場合、"Cannot start a runtime from within a runtime" で panic
- 対処: `tokio::task::spawn_blocking` を使って VLM 抽出をランタイム外で実行するか、呼び出し元が既に tokio コンテキスト外であることを保証する設計に変更

### [High] HTTP API に認証・認可メカニズムが存在しない
- 指摘者: Blue Team Leader, Compliance & Privacy Guard, Ethics & Bias Auditor
- 場所: `core/src/server/handlers.rs:219-234`
- 影響: `host` を `0.0.0.0` に変更した場合、ノートデータが無認証でアクセス可能
- 対処: (1) API キーまたは Basic認証を実装 (2) 外部バインド時に明示的な警告を表示 (3) 認証情報は環境変数で管理

### [Medium] HTTP ハンドラ内の同期ファイル I/O が tokio ワーカースレッドをブロック
- 指摘者: System Architect, Domain Logic Expert
- 場所: `core/src/server/handlers.rs:179`
- 影響: `std::fs::read_to_string` が tokio ワーカースレッドをブロック。並行リクエスト時にスループット低下
- 対処: `tokio::fs::read_to_string` に変更

### [Medium] VLM API キャッシュなし — 再インデックス時に無駄な API 課金
- 指摘者: FinOps Consultant
- 場所: `core/src/indexer.rs:407-470`
- 影響: PDF のハッシュ未変化でも VLM API が再呼び出され、API 課金が発生
- 対処: VLM 抽出結果を DB にキャッシュし、PDF バイナリの SHA-256 と比較

### [Medium] `pdf.rs` 内のマジックナンバーが定数化されていない
- 指摘者: Maintainability Guardian
- 場所: `core/src/pdf.rs:87,171,187,212-218`
- 影響: 閾値の意味が読み取りにくい。意図の伝達が困難
- 対処: `const FULL_WIDTH_RATIO: f32 = 0.8;` 等の命名定数を定義

### [Medium] README.ja.md に HTTP API Server セクションが欠落
- 指摘者: Documentation Architect
- 場所: README.ja.md
- 影響: 日本語ユーザーは `shiotsuchi serve` の存在や API エンドポイント情報を得られない
- 対処: README.md の「HTTP API Server」セクションを日本語に翻訳して追加

### [Medium] VLM モジュールが PDF 内容を外部 API に送信するが、ユーザー同意・開示が不十分
