## 重要指摘事項（優先度順）

### [High] DBスキーマ更新で明示的トランザクションがない
- **指摘者**: System Architect, Domain Logic Expert, Data Integrity Expert, Test Experts
- **場所**: `core/src/db.rs:70-122` (`upsert_note`), `core/src/db.rs:171-176` (`delete_note`)
- **影響**: FTS5削除 → FTS5挿入 → metadata更新の3ステップが個別の自動コミットで実行される。途中でエラー・クラッシュが起きると `notes_fts` と `notes_meta` の間に不整合が生じ、検索でヒットしてもメタデータが欠損する、あるいはその逆の状態になり、データ信頼性が著しく低下する。
- **対処**: `rusqlite::Transaction` を使用して各メソッド内の複数ステートメントを単一トランザクションで包み、`commit()` で確定、失敗時に `rollback()` で復旧可能にする。

### [High] 検索スニペット抽出におけるパストラバーサル・任意ファイル読み出し
- **指摘者**: Red Team Leader
- **場所**: `core/src/search.rs:34-38`
- **影響**: `search()` は DB に格納された `result.path` を `notes_dir.join(&result.path)` でそのままファイル読み出しに使用する。`result.path` に `../etc/passwd` などが含まれる攻撃者製のデータベースを指定した場合、ボルト外の機密ファイルが検索結果のスニペットとして露出する。
- **対処**: `result.path` を vault 内制限で検証。相対パスのみ、`..` なし、`canonicalize` 後に `starts_with` でボルト内制限。シンボリックリンクも拒否。
- **修正状況**: Test Experts により修正済み（`core/src/search.rs` に検証ロジックとテストを追加）

### [High] unsafe deserialize の整合性検証の欠如
- **指摘者**: Red Team Leader
- **場所**: `core/src/tokenizer.rs:63-66`
- **影響**: `Predictor::deserialize_from_slice_unchecked` を `unsafe` ブロック内で使用しており、埋め込みバイト列の整合性をランタイムで検証していない。ビルド成果物への改ざんやバイナリ破損時に未定義動作（メモリ破損・クラッシュ・潜在的なコード実行）につながる。
- **対処**: ビルド時にハッシュ・署名を生成し、ランタイムで `deserialize` 前に検証する。または、安全な `deserialize` メソッド（チェック付き）への移行を検討する。

### [High] ホームディレクトリ取得失敗時のフォールバック先が `/tmp`
- **指摘者**: Ethics & Bias Auditor
- **場所**: `cli/src/config.rs:33`, `mcp/src/main.rs:52`
- **影響**: `dirs::home_dir()` が失敗した場合、SQLiteデータベースが `/tmp/.cache/shiotsuchi/db.sqlite3` に作成される。Unix系OSでは `/tmp` は通常 `1777` 権限で他ユーザーからも読み取り可能であり、個人ノートの全文インデックスが含まれるDBが漏洩するリスクがある。
- **対処**: フォールバックを `/tmp` ではなく、カレントディレクトリ配下（`./.shiotsuchi`）に変更するか、ホームディレクトリが特定できない場合はエラーで終了させる。
- **修正状況**: Test Experts により修正済み（カレントディレクトリ配下への変更）

### [High] 文字列ベースのエラーハンドリング（脆弱な分岐）
- **指摘者**: Maintainability Guardian, Legacy Bridge Architect
- **場所**: `cli/src/main.rs:57`
- **影響**: `e.to_string().contains("unable to open")` により、エラーメッセージの変更・ローカライズ・内部ライブラリのバージョンアップで分岐が即座に壊れる。型安全でなく、将来の修正でデグレの原因になる。
- **対処**: `ErrorCode::CannotOpen` 等のエラーコード種別を使うか、`db_path.exists()` で事前チェックする。

### [High] Semantic Versioning 違反
- **指摘者**: API & Contract Negotiator
- **場所**: `Cargo.toml`（workspace version `0.1.1`）, `CHANGELOG.md`
- **影響**: `shiotsuchi-skill` を依存に持つ外部ユーザーが `0.1.0` から `0.1.1` へのアップデートだけでビルドに失敗する。破壊的変更がメジャー・マイナーバージョンアップなしにリリースされている。
- **対処**: バージョンを `0.2.0` に上げる。または、skill crate を非推奨として残し、完全削除は次のマイナーバージョンアップで行う。

### [Medium] MCPハンドラーでのエラー情報露出
- **指摘者**: Red Team Leader, Blue Team Leader
- **場所**: `mcp/src/main.rs:32`, `mcp/src/handler.rs:29-39`
- **影響**: 内部エラーメッセージ（ファイルパス、SQLite内部エラーなど）がそのままMCPクライアントに返される。攻撃者にシステム情報のリコナissanceに利用される可能性がある。
- **対処**: クライアントには汎用的なエラーメッセージにマッピングして返却し、詳細はサーバー側のログに出力する。
- **修正状況**: Test Experts により修正済み

### [Medium] WALモード未設定によるマルチプロセスDBアクセス競合
- **指摘者**: SRE/Ops Specialist, Tuning Expert
- **場所**: `core/src/db.rs:22`
- **影響**: CLIとMCPサーバーが同時に同一DBにアクセスする可能性があるが、`PRAGMA journal_mode=WAL` が未設定。デフォルトのrollback journalでは書き込み中の読み取りブロックにより「database is locked」エラーやMCPサーバーのレスポンス遅延が発生する。
- **対処**: `Connection::open` 直後に `PRAGMA journal_mode=WAL;` を実行する。
- **修正状況**: Test Experts により修正済み（`core/src/db.rs` に追加）

### [Medium] DBパス解決ロジックの重複（DRY違反）
- **指摘者**: Maintainability Guardian, Refactoring Evangelist
- **場所**: `cli/src/config.rs:36-38` と `mcp/src/main.rs:42-56`
- **影響**: `XDG_CACHE_HOME` → `home_dir` → `.cache/shiotsuchi/db.sqlite3` の同一ロジックが2箇所に展開されている。
- **対処**: `core` または `cli` crate の config モジュールに `default_db_path()` を一元化し、`mcp` crate からも参照する。

### [Medium] MCPツール内でTokenizerキャッシュを使用していない
- **指摘者**: Maintainability Guardian, Edge & Mobile Strategist
- **場所**: `mcp/src/handler.rs:23`
- **影響**: CLI側では `get_tokenizer()` を使用しているが、MCP側ではリクエストごとに `JapaneseTokenizer::new()` を呼び出している。モデル初期化に数秒かかるため、MCPツール呼び出しごとに遅延が発生する。
- **対処**: `handler.rs` でも `core::tokenizer::get_tokenizer()` を使用するように統一する。
- **修正状況**: Test Experts により修正済み

### [Medium] config.toml の読み込みエラーがサイレントに無視される
- **指摘者**: Blue Team Leader, API & Contract Negotiator, Legacy Bridge Architect
- **場所**: `cli/src/config.rs:94-101`
- **影響**: `ShiotsuchiConfig::load()` で `load_from()` のエラーを `unwrap_or_default()` により無視する。ユーザーは意図した設定が無視されていることに気づかない。
- **対処**: 読み込み失敗時に `eprintln!` で警告するか、`Result` を返して呼び出し側でエラーハンドリングする。
- **修正状況**: Test Experts により修正済み（警告出力を追加）

### [Medium] MCPサーバー起動時のDB親ディレクトリ作成処理の欠如
- **指摘者**: Blue Team Leader
- **場所**: `mcp/src/main.rs:46-56`
- **影響**: MCPサーバーは `db_path` の親ディレクトリが存在しない場合に失敗する可能性がある。CLI側では `create_dir_all` を実行しているが、MCPサーバー側では同様の処理が行われていない。
- **対処**: MCPサーバー起動時に `db_path.parent().map(|p| std::fs::create_dir_all(p))` を実行する。
- **修正状況**: Test Experts により修正済み

### [Medium] スリープベースのタイミング依存テスト
- **指摘者**: DX Advocate
- **場所**: `cli/tests/e2e_test.rs:256`
- **影響**: PollWatcherを使ったファイル監視テストで2.5秒程度の固定 `thread::sleep` が複数存在する。flakyになりやすい。
- **対処**: イベント到達をシグナルベースで待つ。または、テスト用タイムアウト値を環境変数で上書き可能にする。
- **修正状況**: Test Experts により修正済み（環境変数化）

### [Medium] 埋め込みモデルのバージョン二重管理
- **指摘者**: Legacy Bridge Architect
- **場所**: `core/Cargo.toml`（`[dependencies]` + `[build-dependencies]` の重複）
- **影響**: `vaporetto` と `ruzstd` が workspace dependencies に一元管理されておらず、バージョンズレで `serialize_to_vec()` と `deserialize_from_slice_unchecked()` のバイナリ形式が不一致になるリスクがある。
- **対処**: ルート `Cargo.toml` の `[workspace.dependencies]` で `vaporetto` と `ruzstd` を一元管理し、各 crate で `version.workspace = true` を共用する。

### [Medium] CLIクレートがE2EテストのためにMCPクレートにdev-dependencyしている
- **指摘者**: System Architect
- **場所**: `cli/Cargo.toml:26`, `cli/tests/e2e_test.rs:15-33`
- **影響**: CLIクレートのdev-dependenciesに `shiotsuchi-mcp` があり、workspace内のクレート間責務が曖昧になる。
- **対処**: E2Eテストをworkspaceルートまたは専用の `e2e/` クレートに移動する。

### [Medium] 設定ファイルのパースエラーが黙って無視される
- **指摘者**: Legacy Bridge Architect
- **場所**: `cli/src/config.rs:94-99`
- **影響**: ユーザーが編集した `config.toml` に構文エラーがあると、エラー通知なしにデフォルト設定が使われる。
- **対処**: 読み込み失敗時に `eprintln!` で警告するか、`Result` を返して呼び出し側でエラーハンドリングする。
- **修正状況**: Test Experts により修正済み

### [Medium] `search()` の LIMIT 値がSQL文字列に直接連結
- **指摘者**: Data Integrity Expert, Tuning Expert
- **場所**: `core/src/db.rs:217-224`
- **影響**: `limit` 引数が `format!` でSQL文字列に直接埋め込まれている。意図しない巨大値や負の値が渡された場合、クエリプランの暴走や予期しない大量データ取得によりシステム負荷が上昇する。
- **対処**: `LIMIT ?` としてパラメータバインド `params![fts5_query, limit as i64]` を使用する。

### [Medium] Rust バイナリワークスペースで Cargo.lock が .gitignore されている
- **指摘者**: Supply Chain Sentinel
- **場所**: `.gitignore:3`
- **影響**: ビルド再現性が失われ、サプライチェーン攻撃や CVE 追跡が困難になる。
- **対処**: `.gitignore` から `Cargo.lock` を削除し、バージョン管理に含める。

### [Medium] スキーママイグレーション機構の不在
- **指摘者**: SRE/Ops Specialist, Data Integrity Expert
- **場所**: `core/src/db.rs:36-67`
- **影響**: 既存DBに対するカラム追加・型変更などのスキーマ進化を管理する仕組みがない。将来のスキーマ進化時に既存ユーザーでデータ不整合やランタイムエラーが発生するリスクがある。
- **対処**: `PRAGMA user_version` をチェックするマイグレーションマネージャーを導入する。
