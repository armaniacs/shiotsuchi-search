## 新たに発見したリスク

- **量子化ベンチマークのスコープ**: f16 vs binary の比較には、既存のテストデータセットでは不十分。実際の検索クエリを使った precision@k 評価が必要になる。ベンチマークコードを書く工数が 1d に追加で必要。
- **Config 共通化の依存関係逆転リスク**: CLI (`shiotsuchi-cli`) → MCP (`shiotsuchi-mcp`) の依存はあるが、逆はない。core crate に Config 型を置くと、CLI と MCP が両方 core に依存する形になり現状の依存関係と矛盾しない。ただし Config 型が CLI 固有のロジック（`load_from`, `resolved_vaults`）を持つと core の責務が曖昧になる。
- **WalkDir ストリーム処理と progress のトレードオフ**: 事前カウントを廃止すると progress の total 数が最初は不明になる。UI 的に「ファイル 3/??? 処理中」のように表示する必要があり、CLI の progress 表示にも変更が必要。

## 未解決の疑問

- 量子化方式のベンチマーク: f16 vs binary、どちらの precision@k が許容範囲か
- Config 型の責務範囲: core に置く Config はどこまでのロジック（load, resolve, validate）を持つべきか

## 決定事項

1. **プラットフォーム**: Mac + Linux を正式サポート。Windows は貢献者がいれば受け入れる。
2. **Windows パーミッション指摘 (S5)**: High → Medium に下げて維持。companion path の PathBuf 修正は別項目として残す。
3. **埋め込み量子化 (D2)**: 着手する。方式選定のためにまずベンチマーク（f16 vs binary の precision@k 比較）を書く。
4. **Config 共通化 (A2)**: core crate に新しい Config 型を定義して統合する。
5. **ONNX optional 化 (P5)**: 現状維持。やらない。
6. **WalkDir ストリーム処理化 (P2)**: 3h 投資して collect 廃止 + 事前カウント廃止を実施する。
7. **build.rs キャッシュ (C1)**: 30m 投資してタイムスタンプベースの再展開スキップを追加する。
