ノートが増えると検索が壊れていきます。

Obsidianで2年ほどノートを書き続けたら、ファイル数が3,000を超えていました。`grep -r "プロジェクト計画" ~/Notes` はまだ動きます。でも「プロジェクト」と「計画」が別々の段落にあるノートはヒットしません。「会議メモ」を検索しても「会議の記録」は出てきません。日本語のテキストを単語で区切れていないのが根本原因で、grepは文字列をそのまま探すだけだからです。

Obsidianのビルトイン検索は速くて便利ですが、CLIから叩けないので他のツールと組み合わせにくいという問題があります。「昨日書いたノートのうち、タグが `#仕事` で本文に『締め切り』が含まれるものをリストアップする」をスクリプトで書こうとすると詰まります。

## 既存ツールで何が足りないか

最初は組み合わせで解決しようとしました。

`fzf` でファイル名からインタラクティブに絞る方法は、ファイル名を覚えていないと使いものになりません。`ripgrep` は高速ですが、やはり文字列マッチなので日本語の形態素を意識しません。「食べる」を検索しても「食べた」「食べて」はヒットしないし、「食」単独で検索すると「食事」「食器」「食欲」が全部引っかかります。

SQLiteのFTS5という選択肢もあります。FTS5はSQLiteに組み込まれた全文検索エンジンで、`unicode61` トークナイザーが使えます。ただし `unicode61` は日本語をほぼ1文字ずつに分割するため、「プロジェクト計画」を検索すると「プ」「ロ」「ジ」… と分解して検索してしまい、精度が出ません。

結局、「日本語を正しく形態素解析して、FTS5に食わせる」という構成以外に答えがないという結論になりました。

## Vaporetto との出会い

Vaporettoは LegalForce Research・東北大学・京都大学の研究者が共同開発した日本語トークナイザーで、MeCab比 約6.8倍速でありながら同等の精度を持ちます。Rustのライブラリとして提供されており、インプロセスで動かせます。

「プロジェクト計画の見直しについて」という文章をVaporettoに渡すと、`プロジェクト 計画 の 見直し に つい て` のようにスペース区切りのトークン列が返ってきます。これをそのままFTS5の `tokenized_content` カラムに入れれば、`unicode61` が各トークンを1単語として扱ってくれます。

```
入力文: 「プロジェクト計画の見直しについて」
           ↓ Vaporetto
トークン: "プロジェクト 計画 の 見直し に つい て"
           ↓ FTS5 unicode61
インデックス: ["プロジェクト", "計画", "見直し", ...]
```

この組み合わせで「プロジェクト」を検索すると「プロジェクトの進捗」「プロジェクト計画」が正しくヒットし、「プログラム」は出てきません。

## 作ったもの

shiotsuchi-search という名前でRustのCLIツールとして実装しました。`cargo install shiotsuchi` でインストールできます。

3,000ノートのインデックスは初回に数十秒かかりますが、2回目以降はSHA-256ハッシュで変更されたファイルだけを再インデックスするため、ほぼ瞬時に終わります。検索は1万件のノートでもサブ秒で返ってきます。

```sh
# インストール
cargo install shiotsuchi

# 初回セットアップ（設定ファイル作成→インデックス）
shiotsuchi init
shiotsuchi index --notes-dir ~/Notes

# 検索
shiotsuchi search "プロジェクト計画"
```

grepでは拾えなかった「計画書を作成した」「計画を立てる」といったノートも、「計画」でまとめて検索できるようになりました。

「ノートが増えれば増えるほど検索が壊れる」という問題は、形態素解析をパイプラインに組み込むことで解消できます。shiotsuchi-searchは、その仕組みをCLIとMCPサーバーという形でパッケージ化したものです。使い方の詳細は別記事で書きます。
