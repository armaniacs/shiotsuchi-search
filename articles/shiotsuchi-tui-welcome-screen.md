`--help` を打つたびに「で、どれを実行すればいいんだっけ」と思うことがあります。コマンド名の一覧は見えても、「最初に何をすべきか」という導線が伝わらないのです。

自分で作ったツールでも同じ問題が起きました。shiotsuchi-search というMarkdownノート検索エンジンを個人で開発しているのですが、気づいたらサブコマンドが15個になっていて、初見の人間がどこから手をつければいいか自分でもわからなくなっていました。v0.4.14 でその問題に向き合い、サブコマンドなしで起動したときにインタラクティブなウェルカム画面を出す仕組みを実装しました。この記事では、その動機・設計・実装のポイントをまとめます。

## shiotsuchi-search とは

[shiotsuchi-search](https://github.com/armaniacs/shiotsuchi-search) は、Rustで書いた日本語対応のMarkdownノート検索エンジンです。日本語トークナイザーの [Vaporetto](https://github.com/daac-tools/vaporetto) と SQLite の FTS5（全文検索拡張）を組み合わせており、ObsidianやLogseqのような大量のノートファイルを高速に全文検索できます。

`cargo install shiotsuchi` でインストールできます。

## サブコマンドが増えると何が起きるか

shiotsuchi-search の典型的な使い方は「`init` で設定ファイルを作り、`index` でノートを取り込み、`search` で検索する」という3ステップです。慣れればシンプルですが、初めて起動した人にはその流れが伝わりません。

`shiotsuchi --help` を打つと確かにコマンド一覧は出ます。しかし `init`、`index`、`search`、`watch`、`doctor`、`tasks`... と並んでいても、どれが必須でどれが任意か、どの順番で実行すべきかは読み取れません。ドキュメントを読んでもらう前提にすると、インストールしてすぐ試してもらえる機会を逃します。

そこで、サブコマンドを何も指定せずに起動したとき—つまり `shiotsuchi` とだけ打ったとき—にウェルカム画面を表示することにしました。

## 画面の全体像

`shiotsuchi` を実行すると、まず状態に応じたバナーが表示されます。

```

║  データの潮流を導く — 日本語対応ノート検索エンジン  ║
║                                                  ║
║  🔰 はじめての方へ                                ║
║     この画面では以下の3ステップを                   ║
║     一緒に進められます                             ║
║     ① 設定ファイルを作る                           ║
║     ② ノートをインデックスする                      ║
║     ③ 検索してみる                                ║
╚══════════════════════════════════════════════════╝
```

:::message
スクリーンショット挿入箇所: ターミナルで実際に `shiotsuchi` を実行したときの全体画面（バナー＋メニュー）

バナーの下にカーソルキーで操作できるカテゴリ別メニューが続きます。

```
実行する操作を選んでください (上下キー:移動, Enter:決定):

  🚀 オンボーディング  (init → index → search を一緒に完了)

  ── セットアップ ──
  init     設定ファイルを作成・編集する
  setup    埋め込みモデルをインストールする

  ── 検索・操作 ──
  search   ノートを検索する
  index    ノートをインデックスする

  ── 情報・メンテナンス ──
  stats    統計情報を表示する
  doctor   環境の状態を診断する

  ── 終了 ──
  exit     終了する
```

上下キーで項目を選んで Enter を押すだけです。

## ユーザーの状態を読んでメッセージを変える

バナーの内容は毎回同じではありません。設定ファイルとデータベースの存在状態を起動時に確認し、バナーの冒頭メッセージをそれぞれ切り替えています。

| 設定ファイル | DB | メッセージ |
|---|---|---|
| なし | なし | 🚀 オンボーディングを開始 |
| あり | なし | ⚡ オンボーディングを続ける |
| あり | あり | 🚀 クイックオンボーディング |

実装はシンプルで、`config_path.exists()` と `db_path.exists()` の2つの真偽値の組み合わせです。たったこれだけですが、ユーザーから見ると「自分の状況をちゃんと把握してくれている」という印象になります。初回起動と2回目以降でメッセージが変わる、という体験はオンボーディングの質を大きく左右します。

## 3ステップのオンボーディングウィザード

メニュー先頭の「オンボーディング」を選択すると、init → index → search を順番に案内するウィザードが起動します。

```
🔰 Step 1/3: 設定ファイルを作成します
  作成先: ~/.config/shiotsuchi/config.toml
  ノート: /Users/yaar/Notes
この内容で設定ファイルを作成しますか？ > Yes

✅ Step 1/3 完了: 設定ファイルを作成しました
Step 2 に進んでノートをインデックスしますか？ > Yes

⚡ Step 2/3: ノートをインデックスします
  ボールト: /Users/yaar/Notes
この内容でインデックスを実行しますか？ > Yes
... (インデックス実行中) ...
✅ Step 2/3 完了: ノートのインデックスが完了しました

🔍 Step 3/3: ノートを検索してみましょう
検索クエリを入力してください > プロジェクト計画
```

:::message
スクリーンショット挿入箇所: ウィザード実行中のターミナル出力（Step 1〜3の流れ全体）
:::

各ステップの前に「この内容で実行しますか？」という確認プロンプトが入るため、途中で止めることができます。設定ファイルが既にある場合は Step 1 をスキップし、DBが既にある場合は再インデックスの有無を確認します。ユーザーの状態に合わせて、必要なステップだけを実行する設計です。

## 技術選択：なぜ ratatui でなく dialoguer か

TUIを実装するとなると、Rustではまず [ratatui](https://ratatui.rs/) が思い浮かびます。イベントループ・ウィジェット・レイアウトエンジンを備えたフルスクリーンTUIフレームワークで、`htop` のようなリアルタイム更新画面を作るには最適です。

ただ、shiotsuchi のウェルカム画面に必要なのは「選ぶ・確認する・入力する」という3種類の操作だけです。

| 操作 | dialoguer | ratatui |
|------|-----------|---------|
| メニュー選択 | `Select` | 自前でウィジェット実装 |
| Yes/No確認 | `Confirm` | 自前でキーハンドラ実装 |
| テキスト入力 | `Input` | 自前でテキストボックス実装 |
| フルスクリーン制御 | 不要 | 必要 |
| イベントループ | 不要 | 必要 |

ratatui はパワフルですが、今回のユースケースには明らかにオーバーエンジニアリングです。フルスクリーンを占有する必要がなく、操作が終わればそのままターミナルのプロンプトに戻る—そういう「コマンドの延長線上にある対話」には [dialoguer](https://crates.io/crates/dialoguer) の方が自然です。

依存クレートが少ないほどビルド時間は短くなります。ratatui は `crossterm` などのバックエンドを引き込むため、ビルドグラフが膨らみます。shiotsuchi は高速検索がコアなので、ツール自体の起動速度やビルド体験も大切にしたい。dialoguer を選んだのはその観点でもあります。

## 実装の細かい配慮

### カラーテーマと NO_COLOR 対応

メニューや確認プロンプトの色は `dialoguer_theme()` で一括管理しています。

```rust
// cli/src/util.rs
pub fn dialoguer_theme() -> Box<dyn dialoguer::theme::Theme> {
    if std::env::var("NO_COLOR").is_ok() {
        Box::new(dialoguer::theme::SimpleTheme)
    } else {
        Box::new(dialoguer::theme::ColorfulTheme::default())
    }
}
```

`NO_COLOR` は [no-color.org](https://no-color.org/) で策定されたデファクトスタンダードで、この環境変数がセットされていればカラーコードを一切出力しません。カラーを解釈できないターミナルや CI 環境での文字化けを防ぐためです。

### 非TTY環境へのフォールバック

`shiotsuchi | less` のようにパイプで繋いだ場合や、CI スクリプト内で実行された場合は標準入出力が TTY ではなくなります。そのまま `Select` を呼び出すとエラーになるため、TTY かどうかを起動直後に確認してフォールバックします。

```rust
let is_tty = std::io::stdin().is_terminal() && std::io::stdout().is_terminal();

if !is_tty {
    println!("{}", messages::WELCOME_NON_TTY_COMMAND_LIST);
    return Ok(());
}
```

非 TTY の場合はコマンド一覧のテキストを静かに出力して終了します。エラーにはなりません。

### メッセージを定数として分離する

ユーザーに表示する日本語メッセージはすべて `cli/src/messages.rs` の定数としてまとめています。`welcome.rs` の実装コードの中にハードコードされた文字列はありません。将来的に英語対応が必要になったとき、あるいはメッセージをまとめて変更したいとき、1ファイルだけ触れば済む構造です。

### エラー時はクラッシュせずメニューに戻る

オンボーディング中にエラーが発生した場合、パニックせずにメニューに戻ります。

```rust
if let Err(e) = run_onboarding(...) {
    eprintln!("⚠️ オンボーディング中にエラーが発生しました: {}", e);
}
// メニューを再表示して続行
```

インデックスに失敗してもウィザード全体が落ちないため、ユーザーは原因を確認してからやり直せます。

### バナーの動的幅

バナーの内側幅は 50 文字固定ですが、オンボーディング完了後のサマリー画面だけはコンテンツに合わせて動的に計算します。

```rust
let inner_w = lines.iter().map(|l| l.len()).max().unwrap_or(46);
```

将来的にメッセージが変わっても枠が崩れません。

## インデックスをゼロから作り直す `shiotsuchi clean`

セットアップに失敗した場合や、ノートが大幅に変わってインデックスをリセットしたい場合は `shiotsuchi clean` を使います。

このコマンドは安全性を優先した設計で、まず既存の DB を `.bak.<timestamp>` 形式でバックアップしてから（直近3件のみ保持）、一時パスに新しい DB を作って全ノートをインデックスし、成功した時点で元のパスにアトミックにリネームします。途中でエラーが起きても元の DB は消えません。シンボリックリンク経由でのファイル削除も防止しています。

## まとめ

CLIツールのサブコマンドが増えると、新規ユーザーへの導線が欠落しがちです。今回の実装を通じて、以下が効いたと感じています。

ユーザーの状態（設定ファイルあり/なし、DBあり/なし）を起動時に検出してメッセージを変えること。非TTY環境でも静かに動作すること。表示テキストを実装コードから分離して定数化すること。エラーでクラッシュせずにメニューへ戻ること。そしてフルTUIフレームワークではなく、ユースケースに合った軽量な対話ライブラリを選ぶこと。

どれも地味ですが、「ツールに育てられた感覚」を持ってもらえるかどうかの差になります。
