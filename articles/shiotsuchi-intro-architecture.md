日本語テキストの全文検索でつまずくポイントは大抵、トークナイザーにあります。英語は単語がスペースで区切られているのでそのままインデックスできますが、日本語は「プロジェクト計画」のように単語の境界がありません。ここをどう解決するかが検索エンジン設計の核心です。

shiotsuchi-searchはVaporetto × SQLite FTS5という組み合わせでこの問題を解いています。この記事では、その仕組みと設計上の判断を解説します。

## 全体の構成

```
Markdownファイル
    │
    ▼
① extract_frontmatter()  ─── title, tags, date を抽出
    │
    ▼
② split_into_chunks()    ─── ヘッダー・段落で分割
    │
    ▼
③ JapaneseTokenizer.split()  ─── Vaporetto で形態素解析
    │
    ▼
④ db.insert_chunks()     ─── FTS5 + file_cache に書き込み
    │
    └── (オプション) Embedder ─── ベクトル埋め込み → vec0 テーブル

検索時:
    query
     │
     ├── FTS モード  → fts_chunks MATCH (BM25 ランキング)
     ├── Vec モード  → embed → vec_chunks KNN (コサイン距離)
     └── Hybrid モード → RRF で FTS + Vec をマージ
     │
     ▼
    extract_snippet() → 結果表示
```

## なぜ Vaporetto をインプロセスで動かすか

日本語対応のFTS5を実現する方法はいくつかあります。

MeCabをSQLite拡張として組み込む方法は、`.so`/`.dylib` のプラットフォーム依存ファイルを配布しなければならず、インストールが複雑になります。サーバー環境ならともかく、個人ツールとして `cargo install` 一発で動いてほしい場合には向きません。

Vaporettoは LegalForce Research・東北大学・京都大学の研究者が共同開発した日本語トークナイザーで、ポイントワイズ線形分類をベースにした形態素解析器です。MeCabと同等の精度を保ちながら処理速度は約6.8倍速く、Rustのライブラリとして公開されています。

Vaporettoを選んだのはRustライブラリとして提供されており、インプロセスで動かせるためです。外部プロセスを立てる必要がなく、バイナリ1本で完結します。Vaporettoのモデルファイル（`.model.zst`）はビルド時に `build.rs` でバイナリに埋め込むこともできるため、配布時の依存関係をゼロにできます。

## トークナイズとFTS5の接続

FTS5の `unicode61` トークナイザーはスペース区切りの単語を前提として設計されています。日本語をそのまま渡すと1文字ずつに分解されてしまいます。

shiotsuchi-searchの解法は単純です。Vaporettoがトークン化した結果をスペース区切りの文字列として専用カラム（`tokenized_content`）に格納し、FTS5はそのカラムだけをインデックスします。

```
入力: "プロジェクト計画の見直しについて議論した"
         ↓ Vaporetto
保存: "プロジェクト 計画 の 見直し に つい て 議論 し た"
         ↓ FTS5 unicode61
インデックス: [プロジェクト, 計画, 見直し, 議論, ...]
```

クエリも同様にトークナイズしてから渡します。「プロジェクト計画」で検索すると `プロジェクト AND 計画` の論理式に変換され、両単語を含むチャンクがBM25でランキングされます。

## チャンク分割

ファイルをそのまま1レコードとして扱うと、スニペット抽出（検索結果の前後文脈）の精度が落ちます。長いファイルでは「どこに該当箇所があるか」が不明瞭になるためです。

shiotsuchi-searchはファイルをチャンク（塊）に分割してからインデックスします。

まずヘッダー（`#`/`##`/`###`）で分割し、ヘッダーセクションが長すぎる場合はさらに空行で分割します。これにより、1チャンクがおおよそ1つのトピックに対応するようになります。

```
# 週次レビュー

## 進捗
...（チャンク1）

## 課題
...（チャンク2）

## 来週の予定
...（チャンク3）
```

各チャンクが独立したFTS5エントリになるため、「来週の予定」というクエリに対してそのセクションだけがヒットし、余分な文脈を含まないスニペットが返ってきます。

## インクリメンタルインデックス

ノートが3,000ファイルあれば、毎回全ファイルを再インデックスするのは遅すぎます。shiotsuchi-searchはSHA-256ハッシュで変更を検出します。

インデックス時に各ファイルのSHA-256ハッシュを `file_cache` テーブルに保存します。次回インデックス実行時に現在のハッシュと比較し、一致していればスキップします。変更・追加・削除されたファイルだけを処理するため、2回目以降のインデックスは大幅に高速化されます。

3,000ファイルのvaultで実測すると、変更なしの場合のインデックス時間は1秒未満です。

## WALモードと並行アクセス

shiotsuchi-searchはCLIツール（`shiotsuchi`）とMCPサーバー（`shiotsuchi-mcp`）の2つのバイナリを持ちます。同じSQLiteデータベースに対して、CLIが書き込みを行いながらMCPサーバーが読み取りを行う場面があります。

SQLiteのデフォルトモード（ジャーナルモード）では、書き込み中に読み取りがブロックされます。WAL（Write-Ahead Logging）モードを有効にすると、書き込みと読み取りが並行して動作するようになります。shiotsuchi-searchはデータベースのオープン時にWALモードを設定しています。

## セマンティック検索（オプション）

FTS5のキーワード検索では、「明日やること」と「TODO リスト」が別の文書として扱われます。セマンティック検索はベクトル類似度で検索するため、意味的に近いテキストをヒットさせられます。

shiotsuchi-searchはONNX形式の埋め込みモデルまたはOpenAI等のAPIを使ってチャンクをベクトル化し、`sqlite-vec`（`vec0` 仮想テーブル）に保存します。検索時はクエリをベクトル化してKNN探索を行います。

FTS（BM25）とVec（コサイン距離）の結果をRRF（Reciprocal Rank Fusion）でマージするHybridモードも実装しています。どちらか一方だけでは拾えないケースをカバーできます。

## タグカウントの O(1) 集計

`stats` コマンドでvaultのタグ集計を表示する際、素直に実装すると全チャンクをスキャンするO(N)になります。

shiotsuchi-searchはインデックス時にタグのカウントを `tag_counts` テーブルにインクリメンタルに書き込みます。`reindex_file` でファイルが更新されるたびにタグカウントを差分更新し、`delete_file_fully` でファイルが削除されたときに減算します。`stats` はこのテーブルを読むだけでO(K)（タグ種類数）で集計できます。

shiotsuchi-searchのコアはこのVaporetto→FTS5パイプラインです。トークナイザーをインプロセスで動かしてバイナリを自己完結させる、という設計は個人ツールの配布コストを大幅に下げてくれました。実際に使ってみたい場合は `cargo install shiotsuchi` で試してみてください。
