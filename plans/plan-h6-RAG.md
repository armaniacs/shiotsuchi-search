# **Shiotsuchi Search RAG 拡張設計仕様書**

本ドキュメントは「Shiotsuchi Search」に RAG（検索拡張生成）機能を統合するための設計案をまとめたものです。  
MCP サーバー設計は [plan-h7-MCP.md](plan-h7-MCP.md) に分離しています。

---

## **1\. 設計理念**

| 原則 | 内容 |
| :---- | :---- |
| **Local-First** | 外部サーバー（Elasticsearch, Pinecone 等）を必要とせず、ローカル環境で完結させる。 |
| **Zero Configuration** | SQLite 1 ファイルにすべてのインデックスを格納し、設定の手間を最小化する。 |
| **Privacy** | ローカル Embedding モデルを利用し、ノートの内容が外部に流出することを防ぐ。 |
| **Extensibility** | MCP を通じて、LLM がノートの内容を「知識」として活用できるようにする。 |

---

## **2\. システムアーキテクチャ**

従来のキーワード検索（FTS5）に加え、意味検索を可能にするベクトル検索エンジンを SQLite の拡張として組み込みます。

| コンポーネント | 採用技術 | 役割 |
| :---- | :---- | :---- |
| **データベース** | SQLite 3 | 永続化・全文検索・ベクトル検索の統合管理 |
| **キーワード検索** | FTS5 (Built-in) | 固有名詞・専門用語・コード片の厳密一致検索 |
| **ベクトル検索** | sqlite-vec | 文章の意味的な類似性に基づく検索 |
| **Embedding** | Qwen3-Embedding-0.6B (ONNX) | `ort` + `tokenizers` クレートで Rust からローカル推論 |
| **非同期ランタイム** | tokio + rayon | I/O・スケジューリングは tokio、CPU 並列は rayon |
| **インターフェース** | MCP (Model Context Protocol) | LLM への知識提供ゲートウェイ |

---

## **3\. データベース・スキーマ設計**

RAG の精度を高めるため、データは「ノート単位」ではなく「チャンク（断片）単位」で管理します。  
現行の `notes_fts` / `notes_meta` テーブルは FTS5 専用として残し、RAG 用テーブルを別途追加します。

```sql
-- ファイル単位のハッシュ・mtime キャッシュ（差分更新の起点）
CREATE TABLE file_cache (
    path     TEXT PRIMARY KEY,
    hash     TEXT NOT NULL,
    mtime    INTEGER NOT NULL,
    model_id TEXT NOT NULL  -- 異なるモデルで生成されたベクトルの混在を防ぐ
);

-- チャンク本文保存用
CREATE TABLE chunks (
    id            INTEGER PRIMARY KEY,
    file_path     TEXT NOT NULL,    -- ファイル単位削除のキー
    chunk_index   INTEGER NOT NULL, -- ファイル内の順序
    parent_header TEXT,             -- 親見出し階層 例: "大見出し > 中見出し"
    content       TEXT NOT NULL
);
CREATE INDEX idx_chunks_file_path ON chunks(file_path); -- 一括削除を高速化

-- キーワード検索用 (FTS5)
CREATE VIRTUAL TABLE fts_chunks USING fts5(
    content,
    content='chunks',
    content_rowid='id'
);

-- ベクトル検索用 (sqlite-vec)
-- float32[1024] は Qwen3-Embedding-0.6B の出力次元
CREATE VIRTUAL TABLE vec_chunks USING vec0(
    chunk_id  INTEGER PRIMARY KEY,
    embedding FLOAT[1024]
);
```

**スキーマのポータビリティ:** `file_cache.model_id` でモデル混在を防ぎ、スキーマバージョンを `PRAGMA user_version` で管理します。SQLite ファイル 1 つをコピーすれば別の PC でもインデックス（ベクトル含む）をそのまま利用できます。

## **4\. チャンク分割戦略**

### **4-1. 再帰的階層分割**

| レベル | 条件 | 分割単位 |
| :---- | :---- | :---- |
| **Level 1** | 常に適用 | Markdown の見出し（`#`〜`###`） |
| **Level 2** | セクションが 1000 文字超 | 空行（段落境界） |
| **Level 3** | 段落間のコサイン類似度が閾値未満 | `find_semantic_breaks` による意味的切れ目 |

**黄金律:**
- チャンクサイズ: 500〜1000 トークン
- オーバーラップ: 隣接チャンクを 10〜20% 重ねることで境界上の情報を取りこぼさない

**Context Enrichment（必須）:** 各チャンクの先頭に親見出し階層をメタデータとして付与します。  
例: `[ファイル名 > 大見出し > 中見出し] チャンクの本文...`

### **4-2. Level 3 の閾値決定：パーセンタイル法**

固定閾値ではなく、ドキュメントごとに全文間の類似度分布を計算し、**下位 10〜15 パーセンタイル**を切れ目とします。ドキュメントの話題密度に自動適応できます。

**チューニングの指針:**

| 現象 | 原因 | 対策 |
| :---- | :---- | :---- |
| チャンクが細切れすぎる | 閾値が高すぎる | パーセンタイルを 5% に絞るか、閾値を 0.05 下げる |
| 1 チャンクに複数話題が混在する | 閾値が低すぎる | パーセンタイルを 15〜20% に上げる |

**デバッグ方法:** `--debug` 実行時に各文間の類似度スコアを表示する。全ノートの平均類似度を統計として出すことが調整の出発点になります。

## **5\. ハイブリッド検索ロジック (Retrieval)**

**RRF (Reciprocal Rank Fusion)** を採用してキーワード検索とベクトル検索を統合します。

1. **FTS5 Query:** BM25 スコアリングによる上位 N 件を取得。
2. **Vector Query:** クエリをベクトル化し、コサイン類似度で上位 N 件を取得。
3. **RRF 統合:** *Score = Σ (1 / (k + rank))* で再計算。FTS5 と Vector のスコアに重み α を掛けて調整する。

### **5-1. 検索モードの選択**

CLI・MCP のどちらからも検索モードを選択できるようにします。デフォルトは `hybrid` です。

| モード | 内容 | 使いどころ |
| :---- | :---- | :---- |
| `fts` | FTS5 のみ（BM25）| 固有名詞・コード片など厳密一致が必要な場合。ベクトルインデックス未構築でも動作する。 |
| `vec` | ベクトル検索のみ（コサイン類似度）| 意味的なあいまい検索に特化したい場合。 |
| `hybrid` | FTS5 + ベクトル検索を RRF で統合 | **デフォルト。** 精度が最も高い。 |

**CLI:** `dive` コマンドに `--mode` フラグを追加します。

```
shiotsuchi dive "クエリ"               # デフォルト: hybrid
shiotsuchi dive --mode fts "クエリ"    # FTS5 のみ
shiotsuchi dive --mode vec "クエリ"    # ベクトル検索のみ
shiotsuchi dive --mode hybrid "クエリ" # RRF 統合
```

MCP での `mode` パラメータは [plan-h7-MCP.md § 1](plan-h7-MCP.md) を参照してください。

### **5-2. パラメータの設計方針：3 段構え**

| 層 | 内容 |
| :---- | :---- |
| **デフォルト値（コード埋め込み）** | グリッドサーチで導き出した最適値を `DEFAULT_K`・`DEFAULT_ALPHA` として定数定義する。 |
| **設定ファイル（config.toml）** | ノートのスタイルに合わせて上書きできる。中級以上のユーザー向け。 |
| **CLI 引数（開発・調整用）** | `shiotsuchi dive --alpha 0.5 "クエリ"` のように実行時に試せる。 |

### **5-2. グリッドサーチによるデフォルト値の決定**

1. 自分のノートから「問いと期待する正解チャンク」のペアを 10 件ほど用意する。
2. *k* ∈ {20, 60, 100}、α ∈ {0.3, 0.5, 0.7} の全組み合わせ（9 通り）で検索を実行する。
3. 各組み合わせで「上位 3 件に期待チャンクが含まれているか」を 10 点満点で採点する。
4. 平均スコアが最高の組み合わせを `default_value_t` に書き込む。

**実装の順序:** まず CLI 引数で手動調整できる状態を作り、感覚を掴んでからグリッドサーチを自動化する。グリッドサーチ本体は `eval` コマンドとして本体コードから分離して実装する。

MCP ツール設計は [plan-h7-MCP.md](plan-h7-MCP.md) を参照してください。

## **6\. 差分更新（Clean-up ロジック）**

1 ファイルが複数チャンクに分割されるため、UPDATE ではなく「一括削除 → 再挿入」を採用します。

### **6-1. 更新フロー**

1. `file_cache` テーブルで `mtime` または `hash` の変化を検知する。
2. `hash` が一致する場合は処理をスキップする（Embedding 計算コストをゼロにする）。
3. 変更があれば `DELETE FROM chunks WHERE file_path = ?` で旧チャンクを一括削除する。FTS・ベクトルテーブルも同一トランザクション内で削除する。
4. ファイルを再チャンク・再ベクトル化して新チャンクを挿入する。
5. 削除と挿入はすべて **1 トランザクション** でラップする（WAL モードにより読み取りはブロックされない）。

### **6-2. バッチ書き込み**

フルスキャン時は複数ファイルをまとめてコミットし、SQLite の書き込みスループットを向上させます。バッチサイズは `--batch-size` CLI 引数で設定可能とし、デフォルトを `100` とします。

SQLite の書き込み性能は fsync 速度に強く依存するため、最適値は環境によって異なります。

| 用途 | 推奨値 | 理由 |
| :---- | :---- | :---- |
| 初期構築（高速化優先） | 500〜1000 | HDD・ネットワークドライブでコミットオーバーヘッドを削減 |
| デフォルト | 100 | SSD 環境での汎用バランス |
| 日常更新（検索優先） | 20〜50 | ロック時間を短くし MCP 検索クエリの待機を防ぐ |

**時間制限コミットの併用:** 「最後の書き込みから N 秒経過したら強制コミット」を `tokio::time::interval` で実装する。バッチサイズに満たない残余ファイルが放置されるのを防ぐ。バッチ境界ごとに `tokio::task::yield_now().await` を挟み、検索クエリ等の割り込みを許容する。

### **6-3. VACUUM：`shiotsuchi dredge` コマンド**

`DELETE` 後もファイルサイズは縮小しません（内部で空き領域としてマークされるだけ）。大量削除（ノート削除・`rebuild_index`）後に手動で回収できる専用コマンドを設けます。

```
$ shiotsuchi dredge
DB size before : 42.3 MB
Vacuuming...
DB size after  : 18.1 MB (57% reclaimed)
```

| オプション | 動作 |
| :---- | :---- |
| （なし） | `VACUUM` を実行し、前後の DB サイズを表示する |
| `--analyze` | VACUUM せず DB サイズと断片化率だけを表示する（実行前の見積もり用） |
| `--incremental` | `PRAGMA incremental_vacuum` を実行する（WAL モードで安全な少量ずつの回収） |

命名の由来：「海底の堆積物をさらって整理する」（浚渫）。既存コマンドの海洋用語規則に沿っています。

## **7\. Rust 推論パイプライン**

### **7-1. 推論の 3 ステップ**

`ort`（ONNX Runtime バインディング）と `tokenizers`（Hugging Face）クレートを組み合わせます。

| ステップ | 内容 |
| :---- | :---- |
| **Tokenize** | `tokenizers` クレートで入力テキストをトークン列に変換する |
| **Inference** | `ort` で ONNX モデルを実行。AVX512・CoreML (Metal)・CUDA を透過的に利用可能 |
| **Pooling + 正規化** | `attention_mask` を考慮した加重平均（Mean Pooling）後、L2 正規化する。`コサイン類似度 = 1 − (L2距離² / 2)` が成立する |

**推論スレッドの制限:** バックグラウンドのベクトル化が検索・UI をブロックしないよう、`ort` のスレッド数を制限するか OS レベルでスレッド優先度を低めに設定します。

### **7-2. モデルのデプロイ方式**

`include_bytes!` による同梱は却下します（0.6B モデルは Vaporetto モデルとは桁違いに大きい）。「標準データディレクトリへの配置規約」をベースに、CLI から上書きできる構成を採用します。

**パス探索の優先順位（起動時に上から順に探索）:**

| 優先度 | 方法 | 用途 |
| :---- | :---- | :---- |
| 1 | `--model-path /path/to/model.onnx`（CLI フラグ） | テスト・一時的な差し替え |
| 2 | `SHIOTSUCHI_MODEL_PATH` 環境変数 | パワーユーザーの固定設定 |
| 3 | `~/.local/share/shiotsuchi/models/`（XDG 標準規約） | 一般ユーザーのデフォルト |

いずれも見つからない場合は `"モデルファイルが見つかりません。'shiotsuchi setup' を実行してください。"` というエラーで終了します。`dirs` クレートはすでに依存に含まれており、XDG パス解決に使用できます。

**`shiotsuchi setup` コマンド:** ユーザーに手動でフォルダを作らせません。

1. 標準データディレクトリ（`~/.local/share/shiotsuchi/models/`）を作成する。
2. モデルの手動配置先を案内する。
3. 配置されたモデルファイルの SHA-256 ハッシュを検証する（[plan-h7-MCP.md § 4-4](plan-h7-MCP.md) 参照）。

### **7-3. 非同期ランタイム：tokio + rayon の役割分担**

| 役割 | 担当 | 理由 |
| :---- | :---- | :---- |
| I/O 待ち・タスクスケジューリング・MCP 通信 | **tokio** | 非同期で「待ち」を効率処理。MCP の JSON-RPC ループと統合しやすい。 |
| CPU 負荷（ONNX 推論・ベクトル計算） | **rayon** | 全コアを使い切るデータ並列に特化。`tokio::task::spawn_blocking` 経由で呼び出す。 |

**初回ベクトル化のバックグラウンド処理フロー:**

1. `tokio::fs` でファイルを非同期にリストアップし、`tokio::sync::mpsc` チャネルにパスを流す。
2. `tokio::spawn` で複数のワーカーを起動する。
3. `tokio::sync::Semaphore` で同時推論タスク数を制限し（例：全コアの半分）、PC が重くなるのを防ぐ。
4. 重い ONNX 推論は `tokio::task::spawn_blocking` でブロッキングスレッドに退避させる。
5. ワーカーが 1 件完了するたびにチャネルへ通知を送り、メインループで `indicatif` プログレスバーを更新する。

**`Ctrl+C` や MCP 切断時の安全な中断:** `tokio::select!` マクロでキャンセル処理を組み込み、中途半端な状態のチャンクが DB に残らないようにします。
