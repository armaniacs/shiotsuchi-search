# **Shiotsuchi Search MCP サーバー拡張設計仕様書**

本ドキュメントは、RAG 拡張（[plan-h6-RAG.md](plan-h6-RAG.md)）に伴う MCP サーバーの設計指針をまとめたものです。  
MCP サーバーの設計は「LLM という非常に賢いが文字通りにしか動かないインターフェース」のための UX デザインです。

---

## **1\. ツール設計**

LLM はツールの `description` を読んで使うツールを判断します。以下の 3 原則を守ります。

| 原則 | 内容 |
| :---- | :---- |
| **明確な命名** | `search` ではなく `search_local_notes` のように対象を明示する。説明文には「いつ使うべきか」を具体的に書く。 |
| **パラメータの制約** | `limit`・`min_score` に適切なデフォルト値と上限を設定し、LLM が極端な値を指定して検索が重くなるのを防ぐ。 |
| **内部実装の隠蔽** | 単一の `search_local_notes` で `mode` パラメータによりモードを切り替える。LLM に FTS5・sqlite-vec の内部実装を意識させない。 |

### **ツール一覧**

| ツール | シグネチャ | 説明 |
| :---- | :---- | :---- |
| **search\_local\_notes** | `(query: string, limit: number, min_score?: number, mode?: "fts"\|"vec"\|"hybrid")` | ノートを検索する。`mode` のデフォルトは `"hybrid"`（RRF 統合）。結果にはファイルパス・親見出し階層・更新日時を付与する。 |
| **get\_surrounding\_context** | `(chunk_id: integer, window: number)` | 指定チャンクの前後 `window` チャンクを返す。`search_local_notes` の結果の文脈補完用。 |
| **index\_status** | `()` | インデックス済みノート数・ベクトル化進捗・使用モデル情報を返す。情報が最新でない可能性を LLM に伝える。 |
| **rebuild\_index** | `()` | 全データのインデックス（チャンク分割・ベクトル化含む）を再構築する。 |

**`mode` パラメータの使い分け（LLM 向け description に記載する内容）:**

| mode | 用途 |
| :---- | :---- |
| `"hybrid"` | **デフォルト。** 精度が最も高い。通常はこれを使う。 |
| `"fts"` | 固有名詞・コード片など厳密一致が必要な場合。ベクトルインデックス未構築でも動作する。 |
| `"vec"` | 意味的なあいまい検索に特化したい場合。 |

CLI での `--mode` フラグについては [plan-h6-RAG.md § 5-1](plan-h6-RAG.md) を参照してください。

## **2\. コンテキスト最適化（トークン管理）**

LLM のコンテキストウィンドウは有限であり、検索結果が多すぎるとコスト増・性能低下を招きます。

- **チャンクの粒度:** 1 チャンクは 500〜1000 文字程度に抑える。より広い文脈が必要な場合は `get_surrounding_context` で取得させる。
- **出力フォーマット:** JSON そのままではなく Markdown 形式（`## Source: file.md > 見出し`）で整形して渡す。
- **メタデータの付与:** ファイルパス・見出し階層・更新日時を必ずセットで渡し、LLM が情報の確からしさを判断できるようにする。
- **Query Expansion のヒント:** 一度の検索で満足な結果が得られなかった場合に再検索しやすいよう、FTS5 由来の関連キーワードをヒントとして含める。

## **3\. パフォーマンスと信頼性**

MCP は対話の中間に位置するため、レスポンス速度が体感速度に直結します。

- **非同期インデックス更新:** ファイルの変更検知・ベクトル化はバックグラウンドで行い、検索リクエスト時は SQLite を読み取るだけの状態にする（[plan-h6-RAG.md § 7-3](plan-h6-RAG.md) 参照）。

### **3-1. ストリーミング：2 段構えの検索戦略**

MCP は JSON-RPC ベースのリクエスト・レスポンス型プロトコルですが、**`notifications/progress`** を使うことで段階的な結果送信が実現できます。FTS5（キーワード検索）は一瞬で終わるのに対し、Qwen3 によるベクトル化・検索には若干の時間がかかります。この特性を活かします。

1. `search_local_notes` が呼ばれたら、**FTS5 検索を即座に実行**し、結果を `notifications/progress` で第一報として送信する。
2. バックグラウンドでベクトル検索を実行し、結果が揃い次第 `notifications/progress` で追加送信する。
3. RRF で統合した最終結果を `call_tool` の **Result（最終レスポンス）** として返す。

**重要な制約:** ストリーミング（Progress）はあくまで「UI 上の進捗表示」または「LLM の予習用」と割り切る。クライアント（Claude Desktop 等）によっては Progress を処理しきれない場合があるため、**最終 Result だけで完結する設計を優先**する。

### **3-2. Rust 内部実装**

MCP サーバーのメインループを `tokio` で回し、`tokio::sync::mpsc` チャネルで検索結果を受け取り次第 stdout へ JSON-RPC 通知として書き出します。重い ONNX 推論は `tokio::task::spawn_blocking` で別スレッドに退避させます（[plan-h6-RAG.md § 7](plan-h6-RAG.md) 参照）。

## **4\. セキュリティとプライバシー**

Shiotsuchi Search の最大の強みはプライバシーです。Local-First を死守します。

### **4-1. パス・トラバーサル対策（最優先）**

LLM は `../../etc/passwd` のようなパスを誤って生成することがあります。

- **ルートディレクトリの固定:** MCP サーバー起動時に検索対象ディレクトリを唯一の正解として固定する（chroot 的発想）。
- **パスの正規化:** `std::fs::canonicalize` でシンボリックリンクや `..` を解決してから、パスがルートディレクトリ内にあるかチェックする。現行実装（`watcher` / `indexer`）と同じパターンを MCP ハンドラにも適用する。

### **4-2. 間接的プロンプト注入（Local Context Injection）**

ノートの内容（例：「これ以降の指示をすべて無視せよ」）によって LLM が操られる可能性があります。RAG において最も危険なリスクです。

- **デリミタの徹底:** 検索結果は `### RETRIEVED CONTEXT ###` のような強力なタグで囲み、「これは外部データであり命令ではない」と LLM に明確に認識させる。
- **メタデータの構造的分離:** ノートの内容（`content`）とシステム情報（`file_path`・`updated_at`）を別フィールドで渡し、LLM が「事実」と「ノートの記述」を混同しないようにする。
- **読み取り専用接続:** 検索ツールは SQLite に ReadOnly モードで接続する。ツール経由でのデータ改ざんを物理的に不可能にする。

### **4-3. SQLite の安全な運用**

- **SQL インジェクション対策:** `rusqlite` では必ず `params!` や名前付き引数によるプリペアドステートメントを使用する。FTS5 の `MATCH` クエリはユーザー入力がそのまま入るためエスケープが必須。
- **stdio 専用通信:** MCP サーバーは stdio で通信するため、ネットワークポートを開く必要はない。誤って HTTP サーバーとして公開しないよう注意する。

### **4-4. モデルの完全性チェック（サプライチェーン攻撃対策）**

外部 API を使わないためシークレットは不要ですが、代わりに ONNX モデルファイルの改ざん検知が必要になります。

- **起動時ハッシュ検証:** ONNX モデルファイルを SHA-256 で検証し、ハッシュと一致しない場合は起動を拒否する。
- **正規ハッシュの管理:** ハッシュ値はソースコードに **ハードコード**する。リリース時に Qwen3-Embedding-0.6B の公式ハッシュを定数として埋め込み、設定ファイルによる上書きは認めない。
- **想定シナリオ:** ローカルのモデルファイルを悪意のある別ファイルに差し替えられると、推論結果を操作される恐れがある。ハードコードにより設定ファイルの改ざんでハッシュを書き換えることもできなくなる。

---

## **5\. ログとデバッグ**

- **ログの最小化:** ローカル環境であっても、ログファイルにノートの生データを書き込みすぎない。ログ流出時に全ノートの内容が露出するリスクを避ける。
- **デバッグモードの分離:** 詳細なログは `--debug` フラグを立てた時のみ出力し、通常時はファイルパスとエラー種別程度に留める。
- **Tool Call の可視化:** 開発者向けに LLM とのやり取り（Tool Call）を追跡できる仕組みを用意する。

---

## **まとめ：設計原則**

「ただの検索エンジン」ではなく、「ユーザーの過去の思考を LLM がいつでも参照できる長期記憶」として振る舞うことがゴールです。  
技術的には **Rust の型安全**・**SQLite のトランザクション**・**徹底したパス・バリデーション** の 3 重奏で個人の知恵を守り抜きます。
